プロジェクト: YouTube Video Selector（YouTube Music Selector）と、その将来の「履歴ビューアー」拡張
作成日: 2026-11-04
位置づけ: **すべての機能別仕様書より上位の命令書。** 最初にこのファイルを最後まで読み、そのうえで作業を始めること。

読み方のラベル:
- **[確認済]** 実データ・実ファイルで確認した事実
- **[推定]** 資料からの推測。実コード・実データで検証が必要
- **[決定]** 依頼者が承認済み（変更は依頼者の承認が必要）
- **[未定]** 未決定。§11 のとおり依頼者へ確認する

## 2. プロジェクトの現状と目標

### 2.1 現行アプリ（既存の作業成果）

- **[確認済]** 現行アプリは、`PROJECT_FLOW.md` に記述された、ビルド工程を持たない JavaScript の PWA。YouTube 視聴履歴（JSONL）を1件ずつ確認し、4ファイル（`likely` / `possible` / `unknown` / `excluded` の `.jsonl`）へ分類する。
- モジュール: `main.js`（状態・書込キュー）、`ui.js`、`file-system.js`、`jsonl-store.js`、`channel-labels.js`、`history.js`（Undo・最大20件）、`backup.js`
- **[確認済]** 実装済み機能: 分類・Undo・チャンネル判定・バックアップZIP・**ジャンプ**（`goTo` を含む）
- **[確認済]** 仕様書作成済み・未実装: **ソート**（`SORT_FEATURE_SPEC.md`）、**検索**（`SEARCH_FEATURE_SPEC.md`）

### 2.2 目標アーキテクチャ（別チャットで作成された設計メモ `youtube-history-app-design.md`）

- Vite + React + TypeScript、`domain/` `services/` `infrastructure/` `features/` の層構造、共通モデル `MediaItem`、サービス別 Adapter、将来のコメント・他サービス対応。
- 目的: YouTube 履歴の一覧・検索・フィルター・タグ、および既存のファイル編集機能との統合。
- 依頼者の意図 [確認済・会話より]: 「これらの機能はいずれ、細分化して**実際のサイトに移行する**」。

### 2.3 私（Claude）の解釈 [推定]

1. **現行PWAは「データを書き換える編集機能」、設計メモの履歴ビューアーは「探して選ぶ機能」で、最終的に1つのサイトへ統合される。** 設計メモの §13（実装前に確定すること）のうち、「既存の編集機能は同じプロジェクトか別アプリか」の答えは「別アプリ（現行PWA）」であり、その形式・スキーマは §0.1 の実データで一部確認できている。
2. 設計メモの実装方針（データ保護・Adapter・FileAccess の抽象化・ローカル完結）は、現行PWAの設計思想と**一致**している。目標アーキテクチャとして採用してよい。
3. ただし設計メモは「新規にゼロから作る」書き方になっている。**16万件の実データを書き換える既存機能を、一度に作り直すのは危険**なので、**段階的に移行する**（§8、ゲートあり）。
4. 設計メモと実データの食い違いは §9 に列挙した。**特に、既存のJSONLに `tags` フィールドは存在しない。**

## 4. 開発手法: DocDD × TDD の運用ルール

### 4.1 基本の流れ（すべての機能・修正でこの順に行う）

```
1. 仕様書の確認・更新   … 日本語で。受け入れ基準を明記
2. 依頼者の承認         … 仕様の意味に関わる変更のみ
3. テストを先に書く     … 受け入れ基準から。まず失敗することを確認
4. 実装                 … テストを通す最小限の変更
5. 全テスト実行         … 1コマンド（npm test）
6. ドキュメント更新     … 同じタスク内で仕様書・DATA_CONTRACT・PROJECT_FLOW を更新
7. 日本語で報告         … §10 の形式
```

- **コードを変えたら、同じタスクで関連ドキュメントも更新する。** これを完了の条件とする（ドキュメントのズレを防ぐ）。
- テスト名は**日本語の仕様項目に対応**させる（例: 「日付のミリ秒が無くても時刻順に並ぶ」）。依頼者がテスト名の一覧を読むだけで、仕様の充足を確認できるようにする。

### 4.2 テストの対象範囲

| 対象 | 方針 |
| :--- | :--- |
| domain の純粋関数（パース・シリアライズ・ソート・検索・移動ロジック） | **自動テスト必須**（TDD の主戦場） |
| データ不変条件（§4.4） | 自動テスト必須 |
| 性能（16万件規模） | 合成データでの計測を自動化（§7） |
| File System Access API / IndexedDB / Service Worker / UI描画 | 自動テストの費用対効果が低い。**UIは薄くして domain に処理を寄せ**、`docs/MANUAL_CHECKLIST.md` の手動確認で補う |

### 4.3 想定外データの扱い（パターン台帳）

16万件には、見えていないパターンが含まれる。**見つけた想定外は台帳に残し、必ずテストにする。**

1. `docs/DATA_CONTRACT.md` に「パターン台帳」を作る。1パターン = ID・内容・件数・扱い・対応テスト。
2. 新しい想定外を発見したら、(a) 台帳に追記、(b) 合成フィクスチャに再現レコードを追加、(c) テストを追加、の3点セットで完了とする。
3. 台帳の初期登録（`likely.jsonl` 661件より [確認済]）:

| ID | パターン | 件数 | 扱い |
| :--- | :--- | :--- | :--- |
| P-001 | `first_played` / `last_played` の**ミリ秒なし**形式（`...56Z`）が混在 | 7 | 文字列比較禁止。`Date.parse` で数値化 |
| P-002 | `title_raw` / `title_clean` / `channel` / `channel_url` がすべて空（`warnings: ["deleted_or_private"]`） | 5 | 並び替えで常に末尾。検索でヒットしても例外を出さない |
| P-003 | `artist_guess` が `null` | 225 | 常に末尾 |
| P-004 | 同名で別 `channel_url` のチャンネル（Aiobahn 2URL、Release - Topic 4URL） | 2名 | チャンネル比較は名前 → URL |
| P-005 | `title_clean` の先頭が `【` `[` `「` や絵文字 | 約70 | ソート用テキストで先頭記号を除去 |

4. 以下は実データで未検証である。**Phase 0 で必ず調査し、台帳に追記する**:
   - 4ファイルをまたいだ `video_id` の重複（同じ動画が複数ファイルに存在しないか）
   - 文字コード（BOM の有無）、改行（CRLF / LF）、末尾改行、空行、極端に長い行
   - 各ファイルで欠けているフィールド・型が違うフィールド
   - `title_clean` と `title_raw` が乖離しているレコード
   - 他のファイル（`possible` / `unknown` / `excluded`）に固有の形式差

### 4.4 データ不変条件（自動テストで常に守る）

| # | 不変条件 |
| :--- | :--- |
| I1 | **往復の意味的一致**: 読込 → 書出 → 再読込で、全レコードの内容が一致する（フィールド・未知フィールド・値・順序） |
| I2 | **往復のバイト一致を測定**: 書出しが元ファイルとバイト単位で異なる場合、差の種類（キー順・空白・Unicodeエスケープ・改行・末尾改行）を報告する。差があれば依頼者に判断を仰ぐ（勝手に「許容」としない） |
| I3 | **分類移動の件数保存**: 移動の前後で、4ファイル合計のレコード数が変わらない |
| I4 | **移動 → Undo で完全に元へ戻る**（内容・位置・順序） |
| I5 | **レコードの同一性**: 移動で内容が変わらない（未知フィールドも保持） |
| I6 | **`video_id` の重複を検出**できる（ファイル内・ファイル間） |
| I7 | **不正行は書込を中断**する（現行の安全方針を維持） |
| I8 | **ソート・ジャンプ・検索は書き込みを一切発生させない** |

### 4.5 品質ゲートと独立点検

- 機能の実装後、**実装とは別のセッション**で「仕様書・テスト・実装が一致しているか」を点検する（同じAIが同じ思い込みでテストを書く危険を避けるため）。点検結果は `docs/REVIEWS/` に記録する。
- 実データのテストは**ローカル実行のみ**。実データ・個人情報は Git に含めない（§5.3）。

### 4.6 依頼者の担当（これ以上を求めない）

- 日本語の仕様書を読み、承認する（コードは読まない）
- テスト名の一覧と、`npm test` の合否を確認する
- スマホ（Android）での手動確認（`MANUAL_CHECKLIST.md` に沿って）

## 5. 絶対ルール

### 5.1 データ保護（最優先）

1. **ユーザーのデータファイル（`*.jsonl`、`channel_labels.json`）を、保存操作なしに変更しない。**
2. 既存レコードの**未知フィールドを削除・改変しない**。JSONLの1行1レコード形式、文字コード、改行形式を既存仕様に合わせる。
3. **書き込みに関わる処理（書込キュー・保存・Undo履歴・バックアップ・`jsonl-store`）を、依頼者の承認なく変更しない。** ソート・検索・ジャンプ・一覧表示は読み取り専用とする。
4. 実データに対する検証は**コピーを使う**。元ファイルに対して書込テストを行わない。
5. 書き込み失敗時に成功したように表示しない。不正行を検知したら処理を中断する（現行方針を維持・緩和しない）。
6. 既存ファイルを新形式へ**一括変換しない**。ファイル名・分類の意味・レコード形式を維持する。
7. 破壊的なコマンド（ファイル削除・強制上書き・履歴の書き換え）を実行する前に、必ず依頼者に確認する。

### 5.2 プライバシー

1. 履歴データを外部へ送信しない。解析・CDN・外部フォント・外部APIを追加しない。
2. **ログ・テスト出力・報告に、動画タイトル・チャンネル名・URL・コメント本文を出さない。** 件数・行番号・パターンIDで報告する（`tools/` のスクリプトも同様）。
3. 読み込んだJSON/JSONLは**信頼できない入力**として検証する（型・サイズ・必須項目）。画面には `textContent` / Reactの通常の描画を使い、`innerHTML` に埋め込まない。

### 5.3 リポジトリ管理

- 実データ（`*.jsonl`、`channel_labels.json`、バックアップZIP）を `.gitignore` に入れ、Git・仕様書・テストフィクスチャに含めない。
- テスト用データは**合成フィクスチャ**（実データの特徴を再現した少数レコード）とする。
- APIキー・個人情報をコミットしない。

### 5.4 変更範囲

- 依頼されたタスクの範囲だけを変更する。ついでのリファクタリングや機能追加をしない。
- 新しい依存（ライブラリ）の追加は、D5・D6 の範囲外であれば**事前に承認を得る**。
- ディレクトリ整理だけのコミットを作らない。ファイルの移動は、そのモジュールをテストで固定してから、機能変更と別のコミットで行う。

## 6. アーキテクチャ方針

### 6.1 レイヤーと依存の向き（現行・目標で共通）

```
UI（components / features の画面部分） → app（状態・コントローラ） → domain（純粋関数）
                                              ↓
                                   services（Adapter：外部形式 ⇄ 共通モデル）
                                              ↓
                                   infrastructure（ファイル・IndexedDB・保存先）
```

| ルール | 内容 |
| :--- | :--- |
| R1 | **domain は DOM・`window`・ストレージ・`state` に依存しない。** import してよいのは domain 同士のみ |
| R2 | domain の関数は純粋関数にする（副作用なし。キャッシュ用 `WeakMap` のみ可） |
| R3 | **UI は domain を直接 import しない。** `app`（`main.js`）が公開する `actions` と表示用データを経由する |
| R4 | infrastructure は domain を import しない（受け渡しは文字列・プレーンデータ） |
| R5 | **外部形式のプロパティ名（`title_clean` など）を知ってよいのは Adapter（現段階では `record-fields`）のみ** |
| R6 | 保存先（preferences・file access）は `app` に**注入**する。`app` が `localStorage` 等を直接参照しない |
| R7 | **UI コンポーネントからファイルAPIを直接呼ばない**（設計メモの方針） |
| R8 | 処理は「純粋関数に寄せ、UIは薄く」。自動テストできる範囲を最大化する |

### 6.2 既存モジュールと目標構成の対応（移行の地図）

| 現行 | 目標の置き場 | 備考 |
| :--- | :--- | :--- |
| `main.js` | `app/` | 状態・コントローラ。分類ロジックは domain へ切り出す（Phase 1） |
| `ui.js` | `components/` `features/*/components` | 画面。domain を直接呼ばない |
| `jsonl-store.js` | `infrastructure/file/jsonlCodec` | パース・シリアライズ・検証 |
| `file-system.js` | `infrastructure/file/browserFileAccess` | `FileAccess` インターフェース化（設計メモ §7） |
| `history.js` | `infrastructure/storage/` | Undo履歴 |
| `backup.js` | `infrastructure/file/` | ZIP生成 |
| `channel-labels.js` | `infrastructure/` ＋ domain の型 | |
| **新規** `record-fields` | `services/youtube/youtubeAdapter` に吸収 | **移行時、`MediaItem` のフィールド直接参照に置き換わる**（ソート・検索は宣言的なキー定義なので影響は小さい） |
| **新規** `sort` / `view-order` / `search` | `domain/` | 設計メモの `features/search/searchHistory.ts` ではなく **domain に置く**（UIは `features/` に残す） |
| **新規** `preferences` | `infrastructure/storage/` | |

- **新規の純粋モジュールは、現在から `src/domain/` に置く。** 既存モジュールは Phase 1 以降、テストで固定してから段階的に移す。
- `MediaItem`（camelCase）に変換する場合も、**`raw`（元レコード）を保持**し、保存時は `raw` に差分だけを反映して未知フィールドを保つ。
- `plays` 配列など大きなフィールドは、`MediaItem` に複製しない（16万件のメモリ重複を避ける。`raw` を参照する）。

## 7. 16万件規模への対応

### 7.1 先に潰すべきリスク（Phase 1 で計測する）

| リスク | 内容 |
| :--- | :--- |
| 書込コスト | 現行は分類のたびに**移動元・移動先の2ファイルを全文シリアライズして書き直す**設計。大きいファイルでは数十MBの書き直しになりうる。キュー集約はあるが、実測が必要 |
| メモリ | 16万件の全レコード + `plays` 配列 + 検索用の正規化文字列 + `order[]`。**Androidブラウザのメモリ上限に注意** |
| 一覧描画 | **16万件を一度にDOM化できない。** 設計メモは「性能問題が出てから仮想スクロール」としているが、**本件は規模が確定しているため、最初から件数上限のページング（「さらに表示」）または仮想化を前提とする** |
| ソート再構築 | `SORT_FEATURE_SPEC.md` は分類ごとに2ファイルの `order` を全再構築する。16万件で遅い場合は差分更新（`splice` / 二分探索挿入）へ切り替える |
| 検索 | 正規化済み文字列のキャッシュ（`WeakMap`）のメモリ消費と、初回構築時間 |

### 7.2 性能目標（案。依頼者の承認を得て確定する）

| 操作 | 目標（案） | 計測環境 |
| :--- | :--- | :--- |
| 起動時の全ファイル読込・パース | 数秒以内で進捗表示 | Node（自動）＋ Android 実機（手動） |
| 分類ボタン → 次の曲が表示 | 体感で即時（100ms 以内） | 実機 |
| ソート切替 | 1秒以内 | 自動＋実機 |
| 検索（入力〜結果表示） | 300ms 以内 | 自動＋実機 |
| 一覧の初期表示 | 1秒以内（件数上限つき） | 実機 |

- 合成データ生成ツール（`tools/gen-synthetic`）で、**実データと同じ分布・特徴（P-001〜P-005）を含む16万件超**を再現し、自動の性能テストに使う。
- 目標を満たさない場合、**書き込み方式の変更（書込の遅延集約、追記ログ + 定期整理など）は、案を依頼者に提示して承認を得てから**行う（§5.1-3）。

## 8. ロードマップ（ゲートつき）

各フェーズの終わりに**成果物・テスト結果を報告し、依頼者の承認を得てから次へ進む。**

### Phase 0: 調査と土台のドキュメント（コード変更なし）
1. 現行コードを全読し、`docs/CURRENT_STATE.md` を作成: モジュール一覧、`state` の形、**`state.index` を使うすべての箇所**、`applyMoveInMemory` の挙動（in-place か新配列か・追加位置）、Undo履歴のスキーマ、書込フロー、`render` の構造。
2. `tools/inspect-data`（読み取り専用）を作成し、4ファイルを分析。出力は**件数・行番号・パターンIDのみ**（§5.2）。
   - 件数、ファイルサイズ、不正行、ファイル内・ファイル間の `video_id` 重複、フィールド集合と型、空値、日付形式、BOM / 改行 / 末尾改行、極端な行長
3. `docs/DATA_CONTRACT.md` を作成（フィールド定義、実データで確認した事実、パターン台帳 §4.3）。
4. `AGENTS.md`（リポジトリ直下・100行程度）を作成: 本書の §4・§5・§6 の要約、コマンド一覧、機能別仕様書へのリンク。
5. `docs/USER_GUIDE.md`（非エンジニア向け日本語）: 起動方法、テスト実行方法、バックアップの取り方、困ったときの手順。
6. `docs/ROADMAP.md`、`docs/DECISIONS.md`（決定記録: 日付・内容・理由）。

**ゲート**: `CURRENT_STATE.md` と `inspect-data` の結果を報告。本書の食い違い（§9）への見解を示す。

### Phase 1: 安全網（既存挙動の固定）
1. テスト基盤の導入（D5: Vitest・ESLint・Prettier。開発専用）。`npm test` 1コマンドで全テストが動く状態にする。
2. `jsonl-store` の往復テスト（I1・I2・I6・I7）。
3. **分類・Undo のロジックを `main.js` から純粋関数へ切り出す**（挙動を変えない。小さな単位で、テストで固定しながら）。その上で I3〜I5 のテスト。
4. 合成データ生成ツールと性能計測（§7）。結果を依頼者に報告。
5. `docs/MANUAL_CHECKLIST.md`（Android 手動確認項目）を作成。

**ゲート**: 全テスト通過、往復のバイト差の有無（I2）、性能計測の結果、§7.2 の目標の承認。

### Phase 2: 技術スタック判断ゲート（D7）
Phase 0・1 の結果を踏まえ、次の選択肢から**推奨案と理由を日本語で提示**し、承認を得る。
- **A. 現行のまま（JS）で機能追加**: 変更が最小。ただし将来の移行コストが残る。
- **B. 同じリポジトリで段階移行（推奨案）**: Vite + TypeScript を導入し、domain から順に TypeScript 化。React は新しい履歴ビューアーのUIに限って導入し、現行PWAは動かし続ける。**書き込み処理はテストで固定してから移す**。
- **C. 設計メモどおり新規プロジェクトを別途作成**: 既存データ形式を読み書きするが、現行PWAとは別管理。二重管理の期間が長くなる。

推奨を B とする理由 [推定]: 16万件の実データを書き換える処理を一度に作り直す危険を避けつつ、設計メモの目標構成へ到達できるため。**ただし Phase 0・1 の調査結果で変わりうる。**

TypeScript の注意: **型はコンパイル時の保証であり、ファイルから読んだデータの安全は保証しない。** 外部入力には実行時の検証（手書きのバリデーション）が必要。検証ライブラリの追加は承認事項。

## 10. エージェントの行動規範（依頼者はWeb開発に不慣れ）

### 10.1 コミュニケーション
- 日本語で、専門用語を避ける。必要なら一文で説明する。
- **選択肢を提示するときは、推奨案と理由を添える。** 「どれがよいか」だけを聞かない。
- 質問は一度に1〜2個まで。曖昧さがあっても、**仮定を明記して進められる部分は進める**（データを書き換える判断は除く）。
- コマンドを依頼者に実行させる場合は、**コピーして貼るだけで動く形**で示す（`npm test` のように1コマンドに集約）。

### 10.2 報告の形式（各タスクの最後）
1. **やったこと**（3行程度）
2. **確認方法**（依頼者が実行するコマンド、またはスマホでの確認手順）
3. **テスト結果**（通過数 / 失敗数。失敗は日本語のテスト名で）
4. **ドキュメントの更新**（更新したファイル）
5. **食い違い・仮定・懸念**（実コードと仕様の差、仕様に無い判断とその理由）
6. **依頼者に承認してほしいこと**（あれば）

### 10.3 してはいけないこと
- 仕様に無い機能の追加、承認のない依存の追加、データ書込処理の無断変更
- テストを通すためにテストの期待値を書き換えること（期待値の変更は仕様変更として扱い、承認を得る）
- 失敗したテスト・遅い処理・不確かな点を報告から省くこと
- 実機で確認していない動作を「動作確認済み」と書くこと
