# 開発命令書：オフライン対応PWA版 JSONL楽曲分類ツール

## 1. 目的

Androidスマートフォンで、ローカルに保存されたYouTubeの視聴履歴由来のJSONLファイルを、1作品ずつ確認・分類できるPWAを実装する。

ユーザーがスマートフォン上で作品のタイトル・チャンネルを確認し、ボタンを押すだけで分類結果を対応するJSONLファイルに反映できることを目的とする。

既存リポジトリがある場合は構成を調査し、既存の仕組みを可能な限り活用する。新規プロジェクトの場合は、依存関係の少ないシンプルな構成を採用する。

計画やサンプルコードの提示だけで終わらず、実際に動作するアプリ、必要な設定ファイル、README、テストまで実装すること。

## 2. 絶対要件

- Androidスマートフォンで利用できること。
- PWAとしてホーム画面にインストールできること。
- 初回セットアップ後は、インターネット接続がなくてもアプリの画面と分類処理を利用できること。
- データはスマートフォン上のユーザーが選択したフォルダに保存すること。
- 既存のJSONLファイルを直接読み書きすること。
- バックエンドサーバー、Python、FastAPI、データベースサーバーを必要としないこと。
- 作品を1件ずつ、スマートフォンの画面を最大限使って表示すること。
- 分類ボタンを押すと、該当データを移動先のJSONLファイルに反映して、次の作品を自動表示すること。
- タイトルやチャンネル名、既存のデータ項目を勝手に改変しないこと。
- ファイルへの書き込みに失敗した場合、データ消失や重複を黙って発生させないこと。
- 外部へのデータ送信、アクセス解析、広告、外部CDNへの依存を実装しないこと。

## 3. 技術構成

新規プロジェクトでは、次の構成を基本とする。

- HTML
- CSS
- Vanilla JavaScript（ES Modules）
- Vite（開発・ビルド環境）
- Web App Manifest
- Service Worker（オフライン対応）
- File System Access API（ローカルファイル操作）
- IndexedDB（ディレクトリハンドルの保存、操作履歴、必要なメタデータの永続化）

React、VueなどのUIフレームワークは、既存プロジェクトで使用中の場合を除き、導入しない。

Viteの開発依存関係は使用してよいが、完成したアプリの実行にサーバーやネットワーク通信を必要としない構成にする。

PWAのキャッシュには、ビルド成果物に対応した方法を使用する。必要であればvite-plugin-pwaなどを導入してよい。ただし、アプリ実行時に外部CDNや外部APIを呼び出さないこと。

## 4. データファイル

ユーザーが選択する1つのフォルダに、次の4ファイルが存在する。

- `likely.jsonl`
- `possible.jsonl`
- `unknown.jsonl`
- `excluded.jsonl`

各行は、1つのJSONオブジェクトを表すJSONL形式である。

サンプル：

```json
{"video_id":"_kTZrIdilRY","url":"https://www.youtube.com/watch?v=_kTZrIdilRY","title_raw":"崩壊3rd公式MV「渡世」挿入歌「Rubia」","channel":"崩壊3rd公式","channel_url":"https://www.youtube.com/channel/UCRmYt_U1lxTwMVQsDl_MFcA","signals":["title:MV","channel:label","repeat:6"],"warnings":[],"play_count":6,"first_played":"2023-02-23T08:15:32.932Z","last_played":"2025-08-25T14:31:21.458Z","ad_plays":0,"title_clean":"崩壊3rd公式MV「渡世」挿入歌「Rubia」","artist_guess":null,"plays":["2023-02-23T08:15:32.932Z","2023-09-08T08:40:20.868Z","2024-11-26T06:55:08.600Z","2024-12-08T13:39:15.615Z","2025-01-11T14:43:43.975Z","2025-08-25T14:31:21.458Z"]}
```

各ファイルの分類の意味：

- `likely.jsonl`：楽曲である可能性が高い。
- `possible.jsonl`：楽曲である可能性があるが、確証が足りない。
- `unknown.jsonl`：現時点では判断できない、または保留する。
- `excluded.jsonl`：今回の楽曲収集対象から除外する。

分類名と意味をUI内に表示すること。

### データの取り扱い

- `video_id`を作品の識別子として利用する。
- レコードの移動時は、元のJSONオブジェクトの全プロパティを維持する。
- `signals`、`warnings`、`plays`、`artist_guess`などの内容を勝手に修正しない。
- JSONLの各行は独立したJSONとして解析する。
- ファイル末尾の改行の有無や空行によってデータを破損させない。
- 空ファイルは0件のファイルとして扱う。
- 不正なJSONがある場合は、ファイル名と行番号を提示し、安全のため書き込みを中断する。
- 既存ファイルが不足している場合は、ユーザーに確認のうえ空ファイルを作成できるようにする。既存データを初期化してはならない。
- 初期読み込み時に、同一の`video_id`が複数のファイルに存在しないか検査し、重複があれば警告する。

## 5. ファイルへのアクセス

画面に「データフォルダを選択」ボタンを用意する。

ユーザーがボタンを押したときに、対応環境では次のAPIを使用してフォルダへの読み書きアクセスを取得する。

`window.showDirectoryPicker({ mode: "readwrite" })`

### 接続手順

1. ユーザーが4つのJSONLファイルのあるフォルダを選択する。
2. アプリが4ファイルの存在を確認する。
3. 4ファイルを読み込み、各行を解析する。
4. ファイルごとの件数を集計する。
5. 読み書き権限を確認し、分類画面を表示する。
6. 再起動時はIndexedDBに保存したディレクトリハンドルを復元できるようにする。
7. 権限が失われている場合は、ユーザー操作によって再許可を求める。

### ブラウザの互換性

File System Access APIを利用できるか、起動時に実行時検査を行う。

必要なAPIが利用できない場合は、理由と対応ブラウザの案内を表示する。機能がない環境で、ファイルの直接更新が可能であるかのように振る舞ってはならない。

フォールバックとして別ファイルのダウンロードが可能であっても、直接編集機能と混同させないこと。

フォルダ選択APIは、対応するセキュアコンテキストで、ユーザーの明示的な操作から呼び出すこと。

## 6. メイン画面

画面全体を使い、1件の作品を大きく表示する。

スマートフォンでの片手操作を優先する。PC用画面の単純な縮小版にはしない。

### 画面上部

以下を表示する。

- 現在処理中のファイル名
- 現在位置と対象件数
- 全ファイルの件数
- 1セッションでの分類済み件数
- データの保存状態
- 別ファイルへの切り替えUI

対象ファイルは切り替え可能とする。初期表示は`unknown.jsonl`を優先してよい。

### 作品情報

1作品について以下を表示する。

1. `title_raw`：最も目立つタイトル表示。
2. `url`：タイトルにリンクを設定し、作品を開けるようにする。
3. `channel`：チャンネル名を表示する。
4. `channel_url`：チャンネル名にリンクを設定する。
5. `play_count`：再生回数。
6. `first_played`：初回再生日時。
7. `last_played`：最終再生日時。
8. `signals`：分類判断の参考となるシグナル。
9. `warnings`：警告情報。
10. `artist_guess`：存在する場合は推定アーティスト名。

フィールドが存在しない、あるいは`null`である場合は適切に省略する。

長いタイトルやチャンネル名は折り返して表示する。画面から文字がはみ出さないようにする。

YouTubeリンクは、新しいタブで開く。リンクを開いてもアプリ側の現在位置や分類状態を失わないこと。

YouTubeへのリンクはオンライン時にのみ利用できるものとし、オフライン時にもアプリの表示・分類処理は継続できること。

## 7. 作品の分類ボタン

画面下部に、押しやすい分類ボタンを配置する。

ボタンのラベルは次のとおり。

- 「楽曲の可能性が高い」→ `likely.jsonl`
- 「楽曲の可能性あり」→ `possible.jsonl`
- 「判断保留」→ `unknown.jsonl`
- 「対象外」→ `excluded.jsonl`

各ボタンには移動先のファイル名も表示する。

ボタンを押したら、該当レコードを現在のファイルから移動先のファイルへ移動し、処理成功後に次の作品を表示する。

移動先が現在のファイルと同じ場合は、レコードの重複追加や不要な上書きを行わない。「このまま次へ」などの操作として扱い、現在の作品をスキップできるようにする。

分類処理中はボタンを無効化し、連続タップによる重複処理を防ぐ。

保存が完了するまでは、成功したように表示してはならない。

最後の作品を処理したときは、完了状態を表示し、別ファイルを選択するか、前の作品に戻ることができるようにする。

## 8. チャンネルの分類

作品自体の分類と、チャンネルの分類は独立して扱う。

作品の分類は4つのJSONLファイルで管理する。一方、チャンネルについては以下の判定を行えるようにする。

- 「楽曲専用チャンネル」
- 「楽曲専用ではない」
- 「チャンネル判定を解除」

チャンネル分類ボタンを押したときは、作品を別のJSONLファイルに移動してはならない。

チャンネル分類は、追加ファイル`channel_labels.json`に保存する。ファイルが存在しない場合は初回のチャンネル分類時に作成する。

保存形式の例：

```json
{
  "https://www.youtube.com/channel/UCRmYt_U1lxTwMVQsDl_MFcA": {
    "channel": "崩壊3rd公式",
    "channel_url": "https://www.youtube.com/channel/UCRmYt_U1lxTwMVQsDl_MFcA",
    "music_only": false,
    "updated_at": "2026-10-25T00:00:00.000Z"
  }
}
```

`music_only`は`true`、`false`、未判定の3状態を区別できる設計にする。未判定はデータの欠如で表現し、`false`と混同しない。

チャンネルURLをキーにする。同じチャンネルに属する複数の作品で、保存済みの判定を参照できるようにする。

既存データの各レコードを改変せず、チャンネル判定は独立したメタデータとして保存する。

## 9. データ移動の安全性

データ保護を最優先とする。

JSONLファイルの更新は、追記だけではなく、対象ファイル全体を正しく再構成して書き戻す方式を基本とする。

各ファイルへの書き込みでは、`createWritable()`、`write()`、`close()`の完了を確認する。

1回の移動処理は、次の手順で実装する。

1. 操作中フラグを立て、分類ボタンを無効にする。
2. 移動元と移動先のファイルを読み直す。
3. ファイルの内容が最後の読み込み時から外部で変更されていないか確認する。変更があれば自動的に上書きせず、再読み込みを要求する。
4. 両ファイルのJSONLが正しく解析できることを確認する。
5. 移動元に対象の`video_id`がちょうど1件存在し、移動先に同じ`video_id`が存在しないことを確認する。
6. 書き込み前の両ファイルの内容を復旧用に保持する。
7. 移動先のファイルを更新する。
8. 更新後の移動先を再読み込みして、対象レコードが1件だけ存在することを確認する。
9. 移動元から対象レコードを削除し、更新する。
10. 更新後の移動元を再読み込みし、対象レコードが存在しないことを確認する。
11. 成功した操作をUndo履歴に登録する。
12. 件数と画面を更新する。
13. 操作中フラグを解除する。

途中で失敗した場合は、復旧可能であれば処理前の内容に戻す。

特に、移動先への書き込み後に移動元の削除で失敗した場合は、移動先への追加を取り消すことを試みる。

復旧にも失敗した場合は、失敗したファイルと復旧状態を明示し、両方の内容を回収できる手段を表示する。データが二重になった、あるいは復旧できていない状態で正常終了としてはならない。

ファイルシステムは複数ファイル間の完全な原子性を保証しないため、可能な限りの復旧に加えてバックアップ機能を用意する。

## 10. Undoとバックアップ

次の機能を実装する。

### Undo

直前に行った作品の移動を取り消せるようにする。

Undo履歴はIndexedDBに保持し、アプリを再起動しても復元できるようにする。少なくとも直近20件を保持する。

Undo実行時も、現在のファイル内容を読み直し、移動先に該当作品が存在し、移動元に存在しないことを確認してから更新する。

外部でファイルが編集されている、あるいは対象作品の重複が発生している場合は、自動復旧を中止して警告する。

### バックアップ

ユーザーがボタンを押すと、4つのJSONLファイルと`channel_labels.json`が存在する場合はその内容もまとめてZIP形式で書き出せるようにする。

ZIP生成に必要なライブラリは、ビルド時にアプリへ同梱する。実行時にCDNから取得してはならない。

バックアップは書き込み前の復旧や誤操作対策として使用する。

## 11. チャンネル情報の検索性

作品を確認する際、チャンネルの判定結果が保存済みであれば、現在の作品情報の近くに表示する。

同じチャンネルが続く場合でも、既存のチャンネル判定を毎回手入力させない。

ただし、チャンネル判定を根拠なく自動確定してはならない。保存済みの判定を表示するだけにする。

## 12. PWAとオフライン対応

以下を実装する。

- `manifest.webmanifest`
- 適切なアプリアイコン（192×192、512×512）
- `display: standalone`
- Service Worker
- 必要なHTML、JavaScript、CSS、アイコンなどのプリキャッシュ
- オフライン時の起動
- キャッシュのバージョン管理
- 古いキャッシュの整理

オフライン状態では、アプリ自身の画面表示、JSONLの読み書き、チャンネル分類、Undo、バックアップ生成が利用可能であること。

外部リンク以外でネットワーク通信を必要としないこと。

初回アクセス時の読み込みとホーム画面へのインストールには、HTTPSで配信されたアプリを使う構成にする。初回読み込みとキャッシュ完了後は、必要なアプリ資産をネットから取得せずに起動できるようにする。

READMEには、静的ホスティングなどを使ったHTTPSでの公開方法と、Androidでのインストール・オフライン動作確認手順を記載する。

ユーザーのJSONLファイルやチャンネル判定データを公開先へアップロードする仕組みを実装してはならない。

## 13. UIデザイン

スマートフォンを最優先に設計する。

- 1画面に1作品を表示する。
- タイトルは十分に大きく読みやすくする。
- 分類ボタンは親指で押しやすい大きさにする。
- 画面下部の操作領域は固定し、長いタイトルでも操作ボタンが見失われないようにする。
- `100dvh`とセーフエリアを考慮し、Androidのステータスバーやジェスチャーナビゲーションと干渉しないようにする。
- 明るい場所でも読みやすいコントラストを確保する。
- 分類の意味は色だけでなく文字でも表す。
- 処理中、保存成功、保存失敗、権限不足、データ異常を明確に表示する。
- 確認やエラーのメッセージは日本語にする。
- 依存するリモートフォントや外部画像を使わない。

## 14. エラー処理

次のケースを想定する。

- 必要なAPIが利用できない。
- ユーザーがフォルダ選択をキャンセルする。
- ファイルが見つからない。
- JSONLが破損している。
- ファイルへの読み取り・書き込みが拒否された。
- 書き込み中にエラーが発生した。
- 同一`video_id`が重複している。
- 他のアプリでファイルが編集されている。
- IndexedDBへの保存に失敗する。
- キャッシュが更新されていない。
- オフライン状態で起動する。

エラーをコンソールに出すだけで済ませず、ユーザーが次に取るべき操作を画面に表示する。

重要なエラーでは、元データを勝手に初期化したり、別の場所へ自動的に移したりしてはならない。

## 15. テストと受け入れ条件

最低限、以下を確認する。

1. サンプルJSONLを読み込み、タイトルとチャンネル名が正しく表示される。
2. タイトルとチャンネル名から正しいURLが開く。
3. 4つの分類ボタンから各JSONLファイルへ正しく移動できる。
4. 移動先に1件だけ追加され、移動元から対象が削除される。
5. `signals`や`plays`など、元のプロパティが維持される。
6. JSONLの空ファイル、複数レコード、空行を正しく処理できる。
7. 破損したファイルに対して、誤って書き込みを行わない。
8. 連続タップしても重複移動しない。
9. Undoで元の分類に戻せる。
10. チャンネル判定を保存し、同じチャンネルの別の作品でも結果を参照できる。
11. バックアップを生成できる。
12. オフライン状態でPWAを起動でき、分類処理を継続できる。
13. 外部でファイルが変更された場合、内容を黙って上書きしない。
14. 書き込みエラー時に、成功したような表示を行わない。
15. Androidの実機で、全画面表示、スクロール、リンク、分類ボタン、ファイルアクセスが正常に動作する。

単体テストではファイル操作ロジックをUIから分離し、テスト用のデータで検証できるようにする。

ビルドおよびテストを実行し、失敗した項目があれば修正する。

## 16. 推奨ファイル構成

既存リポジトリの構成に合理的な理由がある場合はそちらを優先する。新規作成時は次を参考にする。

```text
project/
├── index.html
├── package.json
├── vite.config.js
├── public/
│   ├── manifest.webmanifest
│   ├── icon-192.png
│   └── icon-512.png
├── src/
│   ├── main.js
│   ├── styles.css
│   ├── ui.js
│   ├── jsonl-store.js
│   ├── file-system.js
│   ├── channel-labels.js
│   ├── history.js
│   └── backup.js
├── tests/
│   ├── jsonl-store.test.js
│   └── classification.test.js
├── README.md
└── .gitignore
```

責務は次のように分離する。

- `main.js`：起動処理と画面全体の状態管理。
- `ui.js`：画面表示とイベント処理。
- `jsonl-store.js`：JSONL解析、検証、レコード移動。
- `file-system.js`：ディレクトリ選択、ファイルアクセス、書き込み、権限確認。
- `channel-labels.js`：チャンネル分類の読み書き。
- `history.js`：Undo履歴管理。
- `backup.js`：バックアップ生成。

## 17. 開発の進め方

1. 既存リポジトリがあれば現状を調査する。
2. ローカルファイルの選択・読み書きが対象のAndroidブラウザで利用可能か確認する。
3. まずJSONLの読み込みと安全なレコード移動を実装する。
4. 1作品を全画面表示するUIを実装する。
5. チャンネル分類とUndoを実装する。
6. PWA化とオフライン対応を実装する。
7. テスト、README、エラー表示を整える。
8. ビルド・テストを実行し、残った制約を明記する。

開発途中で不明点があっても、既定値で合理的に判断できる箇所は実装を進める。取り返しのつかないデータ破壊につながる仕様だけは、安全側に倒す。
